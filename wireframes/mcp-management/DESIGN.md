# Growing Travel MCP 관리 와이어프레임

## 1. 목적과 범위

2026-10-27 사용자 요청: 같이 디자인한 MVP 화면을 바탕으로 MCP 연결·관리 기능의 정보 구조와 주요 행동 배치를 와이어프레임으로 만든다. 기존 여행자용 `dist/`와 별도의 운영자 화면 제안이다. 실제 MCP 서버·인증·권한·호스트 설정을 변경하지 않는다. 본 와이어프레임의 동작과 표시는 메모리 안의 예시다.

LazyCodex/OmO의 frontend·레이아웃·검토 기준과 역할별 검토를 적용한다. 별도의 `lazycodex-ai` 이름을 가진 MCP 실행 도구는 현재 도구 목록에 없어 호출했다고 표시하지 않는다. 본 산출물은 원격 서버의 지원 여부나 운영 스택의 확정이 아니다.

## 2. 사용자와 정보 우선순위

운영자가 서버별 연결 상태를 이해하고, 필요한 도구만 사용하도록 구성하며 실패 원인을 확인하는 상황을 대상으로 한다. 전역 탐색은 연결·활동 두 가지다. 도구 설정과 복구는 선택한 연결의 하위 화면으로 배치한다.

1. 어떤 연결을 보고 있는가, 지금 어느 단계까지 확인됐는가.
2. 이 연결이 제공하는 도구와 MVP에서 사용할 위치는 무엇인가.
3. 다음에 할 수 있는 행동과 저장/적용 범위는 무엇인가.

연결 구성 저장·서버 응답·인증·도구 발견·실행 성공은 서로 다른 상태다. 외부 서버 인증 권한과 앱 안의 도구 허용 목록도 구분한다.

## 3. 시각 토큰

선택한 MVP의 흑연 `#202124`, 코발트 `#3651E8`, 흰 바탕과 중립 회색을 재사용한다. 이미지 대신 실제 문구·필드·행을 가진 구조 와이어프레임으로 만든다. 기본은 밝은 화면이며 검토 도구의 밝기 버튼으로 어두운 배치도 확인한다. 이는 OS 설정이나 서버 설정을 바꾸지 않는다. 기존 역·정원 사진을 관리 화면 장식으로 옮기지 않는다.

## 4. 배치와 스크롤

Layout: 검토 도구 - 여섯 화면 사이 이동과 주석 확인 -> scroll-body-shell; scroll owner: document; anti-patterns: 화면 전체를 읽기 어려운 작은 이미지로 축소, 가로 스크롤로 주요 내용 숨김.

Layout: MCP 관리 - 전역 탐색과 연결별 작업 구분 -> sidebar + stack; scroll owner: document; anti-patterns: 같은 축의 중첩 스크롤, 하단 주 버튼이 본문/메뉴를 덮음.

Layout: 연결 목록 - 이름/상태/도구/다음 행동 비교 -> list-detail; scroll owner: document; anti-patterns: 서버마다 중첩 카드, 정상/인증/발견 성공을 하나의 표시로 합침.

Layout: 연결 추가·권한 설정 - 긴 입력 뒤 단일 적용 행동 -> stack + sticky action area; scroll owner: document; anti-patterns: 미확인 입력을 저장 완료로 표시, 미저장 변경을 현재 설정으로 표시.

1440px에서는 왼쪽 전역 탐색, 가운데 와이어프레임, 오른쪽 검토 주석으로 읽는다. 좁은 화면에서는 전역 탐색을 상단 두 항목으로 정리하고 주석은 본문 아래에 둔다. 390px에서도 입력/제목/버튼은 줄바꿈하며 44px 조작을 유지한다. 주 행동은 각 화면의 제목 옆 또는 입력 끝에 한 번만 강조한다.

| 구성 | 상태·역할 |

## 6. 화면별 행동 계약

| 화면 | 주 행동과 위치 | 정보 순서·보조 행동 |
| --- | --- | --- |
| 01 연결 개요 | 연결 추가, 목록 필터 행 오른쪽 | 연결 이름/상태, 사용 위치, 확인 시점. 모바일은 필터 다음 |
| 02 연결 추가 | 연결 확인, 입력 아래. 확인 후 연결 저장 | 이름·주소, 원격 HTTP 범위, 확인 결과 시연 선택. 취소는 개요 복귀. 확인과 저장을 분리 |
| 03 연결 상세 | 도구·접근 설정, 세 가지 상태 요약 다음 | 연결/인증/발견 상태, 도구 목록, MVP 사용 위치. 재확인·활동 이동 |
| 04 도구·접근 | 변경 저장, 설정 아래 | 대상 연결과 적용 범위, 도구 허용 목록, 변경 요약. 취소는 미적용 초안만 되돌림 |
| 05 활동 기록 | 선택 오류의 문제 해결, 해당 행/상세 | 시각·연결·동작·결과, 실패 단계, 진단. 실패한 쓰기 작업 재실행 없음 |
| 06 문제 해결 | 원인별 인증 단계 시연/다시 확인, 원인 설명 아래 | 확인된 실패 지점, MVP 영향, 다음 행동. 원인 불명은 추정하지 않음 |

연결 추가의 원격 HTTP 입력만 구체화하고 로컬 실행형의 프로그램/환경변수/실행 권한은 후속 설계로 둔다. 인증 방식 예시는 서버 지원에 따라 달라지며 모든 서버가 OAuth를 요구한다고 가정하지 않는다. 도구의 읽기/쓰기 설명은 서버 제공 메타데이터일 수 있어 안전성 인증으로 표현하지 않는다.

## 7. 공식 근거와 제안 구분

MCP는 호스트/클라이언트/서버 역할을 구분한다. [공식 아키텍처](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).

도구 발견과 호출은 별개의 작업이다. 본 시안은 발견한 도구와 앱에서 허용한 도구를 구분하는 관리 방식을 제안한다. [공식 서버 개념](https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts).

HTTP 인증은 선택 기능이며 서버/호스트 지원을 확인해야 한다. [공식 Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). 확인일 2026-10-27. 화면 배치·상태명·허용 목록 정책은 이 프로젝트의 설계 제안이다.

## 8. 검증과 남은 범위

브라우저에서 실제로 열어 여섯 화면 이동, 연결 추가의 오류/확인/저장, 허용 목록의 저장/취소, 활동 필터, 복구 시연을 확인한 뒤 결과를 QA.md에 기록한다. 명령 실행 안내만으로 통과라고 쓰지 않는다. 실제 MCP 호스트 통합·OAuth·서버 연결·영속 저장·배포는 산출물 범위 밖이다.
